# Sendproof for Java

Java and Spring Boot bindings for [Sendproof](../../spec/README.md): the embedded workbench UI, OpenAPI discovery, rollback-only **Preview**, trace-producing **Observed Send**, and conformance with the shared Sendproof protocol v1.

| Module | Artifact | Purpose |
| --- | --- | --- |
| [`sendproof-core`](sendproof-core/README.md) | `io.github.mprync:sendproof-core` | Framework-neutral protocol core: capture, preview orchestration, trace store, SQL redaction, UI asset loader. |
| [`sendproof-ui`](sendproof-ui/README.md) | `io.github.mprync:sendproof-ui` | The shared UI bundle as classpath resources. Generated by `tools/pack-ui.mjs`, never copied. |
| [`sendproof-spring-boot`](sendproof-spring-boot/README.md) | `io.github.mprync:sendproof-spring-boot` | Spring Boot (Servlet/MVC) auto-configuration, springdoc discovery, in-process preview dispatch. |
| [`sendproof-jpa`](sendproof-jpa/README.md) | `io.github.mprync:sendproof-jpa` | JPA/Hibernate and Spring JDBC data integration: outer transaction, change and SQL capture. |
| `sendproof-mongodb`, `sendproof-redis`, `sendproof-dynamodb` | `io.github.mprync:sendproof-mongodb` and so on | MongoDB (Preview in a transaction), Redis and DynamoDB (write guard). See [Data stores](data-stores.md). |
| [`sendproof-jdbc`](sendproof-jdbc/README.md) | `io.github.mprync:sendproof-jdbc` | Framework-neutral JDBC enrollment (`PreviewDataSource`), SQL capture and row-change capture. |
| [`sendproof-logback`](sendproof-logback/README.md) | `io.github.mprync:sendproof-logback` | Logback appender that captures a request's logs. |
| [`sendproof-ktor`](sendproof-ktor/README.md) | `io.github.mprync:sendproof-ktor` | Kotlin/Ktor plugin: workbench, in-process preview dispatch, observed send. |

The conformance fixtures live in [`examples/java-spring-fixture`](../../examples/java-spring-fixture) and [`examples/kotlin-ktor-fixture`](../../examples/kotlin-ktor-fixture).

## Quick start (Spring Boot, JPA)

```kotlin
dependencies {
    implementation("io.github.mprync:sendproof-jpa:0.1.0-alpha.2")      // brings spring-boot, core and ui
    implementation("org.springdoc:springdoc-openapi-starter-webmvc-api:2.8.17")  // optional: OpenAPI discovery
}
```

```properties
# application-dev.properties. Sendproof is off unless this is set.
sendproof.enabled=true
```

```java
@RestController
class OrdersController {
    @SendproofPreview                       // opts this operation in to Preview and Observed Send
    @PostMapping("/orders")
    ResponseEntity<Order> create(@RequestBody NewOrder order) { /* @Transactional service call */ }
}
```

Configuration can also be written in code with `Sendproof.builder()` (see the [Spring Boot README](sendproof-spring-boot/README.md#code-configuration-sendproofbuilder)); properties supply the environment gating either way.

Open `http://localhost:8080/sendproof/`. `GET /sendproof/_api/capabilities` is the discovery document.

## Preview sessions and journeys

Enable Sendproof with `sendproof.enabled=true` in Spring Boot or `enabled = true` in Ktor and configure your Preview
provider and store hooks. Capabilities advertise `previewSessions: true` when every rollback-capable store can keep its
transaction between requests. Signed-in callers use the same stable subject resolver as Observed Send
(`traceOwnerResolver` in Spring Boot and `traceOwner` in Ktor).

Put `store.arazzo.json` and `store.expect.json` together in `src/main/resources/journeys/`. In Spring Boot, register a
`Sendproof` bean built with `Sendproof.builder().journey("journeys/store.arazzo.json").build()`. In Ktor, call
`journey("journeys/store.arazzo.json")` in `install(Sendproof) { ... }`. Both also accept a filesystem `Path`.
Use the application-relative OpenAPI URL in the Arazzo `sourceDescriptions`. Discovery and the served Arazzo document
include the application's path base.

### Code-defined journeys

Expose a stable `operationId` for each step in your OpenAPI document. In Spring Boot, register a `Sendproof` bean like this:

```java
import io.github.mprync.sendproof.core.Journey;
import io.github.mprync.sendproof.spring.Sendproof;

record LookupInputs(String id) {}

@Bean
Sendproof sendproof() {
    var lookup = Journey.define("orderLookup").name("Order lookup")
            .inputs(LookupInputs.class).defaultInput("id", "sample-order")
            .step("load", "getOrder", step -> step
                    .parameter(Journey.In.PATH, "id", Journey.inputRef("id"))
                    .succeedsWith(200)
                    .expectWrites(writes -> writes.nothing()));
    return Sendproof.builder().journey(lookup).build();
}
```

Use the same fluent API from Kotlin. Pass the definition to `journey(lookup)` inside `install(Sendproof) { ... }`, and set
`journeyOpenApi = { openApiJson }` to supply the same parsed JSON that your `openApiUrl` route serves. Spring Boot reads
its configured OpenAPI endpoint on startup. If the endpoint requires authentication or runs outside the embedded
server, supply the same JSON through an `OpenApiDocuments.primaryDocument()` override.

Code and file journeys can be registered together. Code journeys appear in capabilities with `source: "code"`. In
Development, a missing operation, input, or step output fails startup with the offending journey and step. In other
environments Sendproof logs the error and skips that journey.

Start the API in CI and run journeys with the Sendproof CLI:

```sh
npx @sendproof/cli journeys run orderLookup --api http://localhost:8080 --junit report.xml
```

The CLI uses Preview by default and returns a failing exit code if the journey fails. Pass `--inputs inputs.json` to
override defaults. For an API without Preview sessions or a Send-only journey, use a disposable test environment and
pass `--mode send --yes --allow-send` in Development. See the [CLI README](../node/cli/README.md) for authentication
and Send options.

## Safety model

- **Explicit opt-in.** Nothing is registered unless `sendproof.enabled=true`. Even then it stays off while a `prod` or `production` profile is active, unless `sendproof.allow-in-production=true` (a warning explains the refusal).
- **The host stays in charge.** Preview rewrites `/sendproof/_preview/<path>` to the original path *before* Spring Security, then runs the real filter chain, routing, authorization, validation and handler in the same thread. Mark writes with `@SendproofPreview` or `sendproofPreview`. A session also permits unmarked GETs, subject to the host's authorization and any explicit Preview refusal.
- **Rollback-only execution.** A standalone Preview rolls back before returning its envelope. A session keeps successful steps uncommitted until it ends so subsequent steps can read them.
- **Escapes are blocked.** During a preview a nested `REQUIRES_NEW` transaction, or a data-changing statement on a connection with no transaction, is refused before it can persist.
- **Secrets stay out of captures.** SQL values are hidden unless the environment is development-like (`sendproof.sql.include-parameter-values`), and values bound to secret-named columns or in secret-named statements are always `[REDACTED]`. Discovery never contains connection strings.

## Build and test

JDK 17 or newer. Gradle is provided by the wrapper; `scripts/jdk.sh` picks a suitable JDK when the default is older.

```sh
sh adapters/java/scripts/gradle.sh test                         # unit and integration tests
sh adapters/java/scripts/gradle.sh :spring-fixture:bootJar      # builds the conformance fixture
node tests/conformance/run.mjs java-spring                      # shared HTTP conformance runner
sh adapters/java/scripts/gradle.sh :ktor-fixture:installDist    # builds the Ktor fixture (runner id kotlin-ktor)
```

The Gradle home is project-local (`adapters/java/.gradle-home`), so the first run needs network access to fetch Gradle and Maven Central dependencies. The runner starts the fixture with `sh adapters/java/scripts/run-fixture.sh` and sets `PORT`, `BENCH_PATH_BASE` (the servlet context path) and `BENCH_SCENARIO`.

`./gradlew publish` writes a Maven layout to `build/repo` for inspection. The UI bundle is produced by running `node tools/pack-ui.mjs` during `:sendproof-ui:processResources`, so Node is required to build from source.

## Tested versions

JDK 17.0.15, Gradle 9.2.0, Kotlin 2.3.21, Ktor 3.6.1, Spring Boot 3.5.16 (Spring Framework 6.2, Tomcat 10.1), Hibernate 6.6, springdoc 2.8.17, datasource-proxy 1.11.1, H2 2.3. Spring Boot 4, WebFlux, other servlet containers and other databases are not tested.

## Known limits

- Preview needs synchronous handlers. Asynchronous return types (`Callable`, `DeferredResult`) fail the preview.
- Only entity writes show as row changes. Bulk JPQL/native statements and `JdbcTemplate` writes appear as SQL log entries.
- A write that does not use Spring-managed transactions (`dataSource.getConnection()` with manual commit) cannot be enrolled; the autocommit guard refuses plain DML but not manual-commit connections.
- Work moved to other threads is not captured (logs, effects, SQL).
- JDBC drivers do not report parameter names. Names are inferred from the SQL (`name = ?`, `insert into t (a, b)`, `? as alias`) and fall back to `p<n>`.
- Error bodies the container renders from `sendError` (the `/error` page) are not part of a preview's inner body; enable `spring.mvc.problemdetails.enabled` or handle errors in `@ControllerAdvice` for a body.

MongoDB, Redis and DynamoDB are covered only through the clients you hook. [Data stores in the Java and Kotlin binding](data-stores.md) covers setup, the `preview: false` mark and what each store does in a Preview.
