# Test Bench for Java

Java and Spring Boot bindings for [Test Bench](../../spec/README.md): the embedded workbench UI, OpenAPI discovery, rollback-only **Preview**, trace-producing **Observed Send**, and conformance with the shared Bench protocol v1.

| Module | Artifact | Purpose |
| --- | --- | --- |
| [`testbench-core`](testbench-core/README.md) | `dev.testbench:testbench-core` | Framework-neutral protocol core: capture, preview orchestration, trace store, SQL redaction, UI asset loader. |
| [`testbench-ui`](testbench-ui/README.md) | `dev.testbench:testbench-ui` | The shared UI bundle as classpath resources. Generated by `tools/pack-ui.mjs`, never copied. |
| [`testbench-spring-boot`](testbench-spring-boot/README.md) | `dev.testbench:testbench-spring-boot` | Spring Boot (Servlet/MVC) auto-configuration, springdoc discovery, in-process preview dispatch. |
| [`testbench-jpa`](testbench-jpa/README.md) | `dev.testbench:testbench-jpa` | JPA/Hibernate and Spring JDBC data integration: outer transaction, change and SQL capture. |
| [`testbench-jdbc`](testbench-jdbc/README.md) | `dev.testbench:testbench-jdbc` | Framework-neutral JDBC enrollment (`PreviewDataSource`), SQL capture and row-change capture. |
| [`testbench-logback`](testbench-logback/README.md) | `dev.testbench:testbench-logback` | Logback appender that captures a request's logs. |
| [`testbench-ktor`](testbench-ktor/README.md) | `dev.testbench:testbench-ktor` | Kotlin/Ktor plugin: workbench, in-process preview dispatch, observed send. |

The conformance fixtures live in [`examples/java-spring-fixture`](../../examples/java-spring-fixture) and [`examples/kotlin-ktor-fixture`](../../examples/kotlin-ktor-fixture).

## Quick start (Spring Boot, JPA)

```kotlin
dependencies {
    implementation("dev.testbench:testbench-jpa:0.1.0-alpha.1")      // brings spring-boot, core and ui
    implementation("org.springdoc:springdoc-openapi-starter-webmvc-api:2.8.17")  // optional: OpenAPI discovery
}
```

```properties
# application-dev.properties. Test Bench is off unless this is set.
testbench.enabled=true
```

```java
@RestController
class OrdersController {
    @TestBenchPreview                       // opts this operation in to Preview and Observed Send
    @PostMapping("/orders")
    ResponseEntity<Order> create(@RequestBody NewOrder order) { /* @Transactional service call */ }
}
```

Configuration can also be written in code with `TestBench.builder()` (see the [Spring Boot README](testbench-spring-boot/README.md#code-configuration-testbenchbuilder)); properties supply the environment gating either way.

Open `http://localhost:8080/bench/`. `GET /bench/_api/capabilities` is the discovery document.

## Safety model

- **Explicit opt-in.** Nothing is registered unless `testbench.enabled=true`. Even then it stays off while a `prod` or `production` profile is active, unless `testbench.allow-in-production=true` (a warning explains the refusal).
- **The host stays in charge.** Preview rewrites `/bench/_preview/<path>` to the original path *before* Spring Security, then runs the real filter chain, routing, authorization, validation and handler in the same thread. A handler must carry `@TestBenchPreview`, otherwise the preview is refused with 409.
- **Rollback is confirmed, not assumed.** The result is a confirmed envelope only if the handler completed, the response stayed under 1 MiB, the rollback succeeded and the session was disposed. Anything else is a non-success status without `rolledBack`.
- **Escapes are blocked.** During a preview a nested `REQUIRES_NEW` transaction, or a data-changing statement on a connection with no transaction, is refused before it can persist.
- **Secrets stay out of captures.** SQL values are hidden unless the environment is development-like (`testbench.sql.include-parameter-values`), and values bound to secret-named columns or in secret-named statements are always `[REDACTED]`. Discovery never contains connection strings.

## Build and test

JDK 17 or newer. Gradle is provided by the wrapper; `scripts/jdk.sh` picks a suitable JDK when the default is older.

```sh
sh adapters/java/scripts/gradle.sh test                         # unit and integration tests
sh adapters/java/scripts/gradle.sh :spring-fixture:bootJar      # builds the conformance fixture
node tests/conformance/run.mjs java-spring                      # shared HTTP conformance runner
sh adapters/java/scripts/gradle.sh :ktor-fixture:installDist    # builds the Ktor fixture (runner id kotlin-ktor)
```

The Gradle home is project-local (`adapters/java/.gradle-home`), so the first run needs network access to fetch Gradle and Maven Central dependencies. The runner starts the fixture with `sh adapters/java/scripts/run-fixture.sh` and sets `PORT`, `BENCH_PATH_BASE` (the servlet context path) and `BENCH_SCENARIO`.

`./gradlew publish` writes a Maven layout to `build/repo` for inspection. The UI bundle is produced by running `node tools/pack-ui.mjs` during `:testbench-ui:processResources`, so Node is required to build from source.

## Tested versions

JDK 17.0.15, Gradle 9.2.0, Kotlin 2.3.21, Ktor 3.6.1, Spring Boot 3.5.16 (Spring Framework 6.2, Tomcat 10.1), Hibernate 6.6, springdoc 2.8.17, datasource-proxy 1.11.1, H2 2.3. Spring Boot 4, WebFlux, other servlet containers and other databases are not tested.

## Known limits

- Preview needs synchronous handlers. Asynchronous return types (`Callable`, `DeferredResult`) fail the preview.
- Only entity writes show as row changes. Bulk JPQL/native statements and `JdbcTemplate` writes appear as SQL log entries.
- A write that does not use Spring-managed transactions (`dataSource.getConnection()` with manual commit) cannot be enrolled; the autocommit guard refuses plain DML but not manual-commit connections.
- Work moved to other threads is not captured (logs, effects, SQL).
- JDBC drivers do not report parameter names. Names are inferred from the SQL (`name = ?`, `insert into t (a, b)`, `? as alias`) and fall back to `p<n>`.
- Error bodies the container renders from `sendError` (the `/error` page) are not part of a preview's inner body; enable `spring.mvc.problemdetails.enabled` or handle errors in `@ControllerAdvice` for a body.
